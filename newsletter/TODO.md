# Newsletter Sender — TODO & Architecture

## Текущая проблема

- Lambda timeout = 5 мин, а отправка ~4000 писем занимает ~9 мин
- При таймауте Lambda async автоматически делает 2 ретрая → 3 отправки одного кампейна
- Нет idempotency: каждый ретрай начинает с первого контакта заново
- По мере роста базы проблема будет усугубляться

---

## Варианты архитектуры

### Вариант 1 — SQS Fan-out (рекомендуется)

**Как работает:**
1. `newsletter-api` при запуске кампейна кладёт каждый контакт как отдельное сообщение в SQS очередь
2. `newsletter-sender` триггерится SQS, обрабатывает по 10 писем за инвокацию
3. Lambda живёт секунды, а не минуты — никаких таймаутов
4. SQS сам управляет ретраями на уровне отдельного сообщения, не всей рассылки
5. Dead Letter Queue (DLQ) для писем, которые не удалось отправить

**Плюсы:**
- Масштабируется до бесконечности
- Ретраи на уровне одного письма, не всего кампейна
- Параллельная обработка (много Lambda инстансов одновременно)
- Встроенная idempotency через SQS MessageDeduplicationId

**Минусы:**
- Нужно добавить SQS в template.yaml
- Сложнее отслеживать прогресс кампейна в реальном времени

---

### Вариант 2 — Step Functions

**Как работает:**
1. Step Functions orchestrates: chunk список → invoke Lambda per chunk → wait → next chunk
2. Встроенное управление состоянием, ретраями и паузами

**Плюсы:**
- Видно прогресс в консоли AWS
- Гибкий flow (можно добавить паузы, ветвления)

**Минусы:**
- Дороже (Step Functions платные по transitions)
- Сложнее в коде

---

### Вариант 3 — Chunking (быстрый фикс)

**Как работает:**
- Разбить список на чанки по ~500 контактов
- API Lambda вызывает N sender Lambda'ов параллельно, каждый берёт свой чанк
- Каждая Lambda укладывается в таймаут

**Плюсы:**
- Минимальные изменения кода
- Быстро сделать

**Минусы:**
- Не решает проблему при дальнейшем росте базы
- Ретраи всё ещё на уровне чанка, не одного письма
- Нет настоящей idempotency
